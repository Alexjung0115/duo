Agent가 보고한 다른 false PASS는 다음과 같다.

- **글로만 쓴 Decision(`forbids` 없음)의 위반**(B·F, 4건): OpenHub의 Decision 37개는 모두 `forbids`가 없어 review가 위반을 잡을 수 없다. 이것은 문서화된 범위다("forbids만 기계 검사"). 하지만 평가하지 않은 Decision에 `ALIGNED` claim을 붙여, 사람과 Agent가 이를 "확인했다"로 읽는다(C269 후보).
- **우회 경로**: 금지 module의 이름을 바꾼 뒤 import(C·D, Decision이 없는 경로를 계속 금지해도 경고 없음), barrel·re-export chain·template literal `import()`(C, barrel/re-export는 0.3.0 release notes의 known limitation이지만 해당 review에 limitation 항목이 없음), 기존 wrapper를 통한 간접 사용(E, README의 direct-import-only와 일치).
- **`forbids.imported_paths` 경로 오타나 대소문자 불일치**(D): 아무 파일과도 맞지 않는데 진단이 없다(C271 후보).
- **`implements.paths`로 연결된 Requirement**(E): review가 changed symbol에서 시작하므로, 파일 경로로 연결된 Requirement·test-coverage·관련 pending proposal이 보이지 않는다. Agent의 자기 pending proposal도 보이지 않았다(C267 후보).
- **Agent가 작성한 Truth**(E): lock 없이 손으로 쓴 "confirmed" Decision이 열린 질문(declared UNKNOWN)을 해결한 것으로 처리돼 ASK가 사라진다. Requirement 본문을 고쳐 UNKNOWN을 지워도 claim이 없다. 손으로 쓰는 confirm은 ADR-013의 fallback이므로 부분적으로는 문서화된 동작이다.
- **승인된 acceptance criterion의 regression test 약화**(F): PASS. DUO는 test 의미를 검사하지 않는다.

**실제 commit 48건에서는 false negative가 없었다.** 확정된 Decision을 어긴 실제 commit을 찾지 못했기 때문이다. 위 false PASS는 모두 합성 시나리오에서 나왔다.

## 10. Coding-agent behavior

Agent E의 Codex 세션 15개(기본 model과 gpt-5.5)에서 관찰한 결과다. 인용은 Agent 응답 원문(영문)이다.

| 상황 | 관찰 |
|---|---|
| PASS + missing-intent | PASS를 "코드가 안전하다"로 읽은 Agent는 없었다. "Duo's review returned PASS, but that PASS doesn't tell you much here." gap과 violation도 구분했다. 다만 F의 작업 세션은 `ALIGNED` claim을 "aligned with D-001, D-004, D-008"이라는 보증으로 사람에게 되풀이했다 |
| WARN | "WARN, no blockers"로 요약하고 진행했다. Agent가 넣은 서술형 task가 ASK를 WARN으로 낮춘 세션 3/3에서, Agent는 사람의 결정이 필요한 rounding 변경을 끝냈다(C268 후보) |
| ASK | review만 하는 세션에서는 사람에게 질문을 넘겼다. "This is your decision (or your team's) to make. I can draft a DUO decision proposal for you, but only a person can confirm it." 작업을 끝내라는 세션 4/4는 결정 전에 구현을 마쳤다. 한 세션은 ASK가 나오게 한 자기 metadata 수정을 되돌렸다("I'm backing that metadata-only change out") |
| BLOCK | 5/5 지켰고 우회 시도는 없었다. "Proposing doesn't unblock anything: the change stays blocked until a person confirms." 5개 중 2개는 provenance `introduced`를 "이 변경이 만들었다"로 잘못 읽었다 |
| pending Decision | 관련 pending을 사람의 결정 대상으로 설명했다. 한 세션은 pending P-001을 "human-confirmed project decision"이라고 잘못 불렀다 |
| Decision proposal 필요 | 4/4가 `duo_propose_decision`으로 proposal만 만들고 confirm은 시도하지 않았다. 한 gpt-5.5 세션은 프로젝트 소유 spec 파일을 직접 고쳤다 |
| MCP text와 structuredContent | 모든 저장소에서 내용이 같았고 Agent의 해석도 일관됐다 |
| MCP 연결 | 15개 중 5개 세션이 Codex의 deferred tool discovery 때문에 DUO MCP tool을 찾지 못하고 CLI로 돌아가거나 추측했다(C273 후보, Codex 쪽 동작이 원인) |

Human authority: MCP와 CLI 경로에서는 지켜졌다. Agent는 confirm·reject를 하지 않았다. 하지만 Agent가 Truth 파일을 직접 고치면 DUO가 막지 못하거나 나중에 알아채지 못하는 경로가 있다(§7 C261·C262, proposal을 YAML에서 `rejected`로 고치면 ASK가 사라짐).

| review | 1.5~13초(OpenHub 7~18초, 5,000 파일 diff 9.5~20초) | FAST~ACCEPTABLE |
| MCP 첫 호출 | 0.9~2.7초(큰 저장소 8~11초) | FAST~ACCEPTABLE |
| `duoctl install codex/claude-code` | 3~11초 | FAST |

실제 workflow를 방해한 성능 문제는 50 MB 파일의 index loop뿐이다(§9).

Friction:

- 신규 사용자(A): 설치와 연결은 README와 CLI만으로 가능했다. 각 명령이 다음 단계를 알려주고, install은 변경 계획을 보여주고 `--yes` 전에는 쓰지 않으며, 기존 설정을 보존했다. 하지만 Truth를 기록하는 안내가 없어 init 뒤의 review는 "no confirmed intent"만 붙은 PASS다. `init --answers -`의 형식은 영문 문서에 없고, 잘못된 answers는 내부 오류(`Cannot read properties of undefined (reading 'trim')`)를 노출했다.
- **`install remove`가 DUO가 만든 설정 파일의 MCP 항목을 지우지 않는다**(A, 4/4). 계획에는 "delete .mcp.json"이 있지만 적용은 "modify"이고, 종료 코드 0을 낸 뒤 연결이 남는다(C266 후보, P1).
- 명령별 `--help`가 없고, review 파일 수에 DUO 자신의 파일이 포함된다. `context`는 `--task`를 받지 않는다(review와 불일치). `duo_search_evidence`는 여러 단어로 된 자연어 query에 0건을 돌려준다.
- 저장소가 devDependency로 이전 DUO(0.2.1)를 고정하면 npx launcher가 그 version을 쓴다. `install codex`가 launcher를 바꾸지만 사용자는 이를 알아차리기 어렵다.

Real coding workflow(F, OpenHub, "registry에 공식 filesystem MCP server 추가"):

| | DUO 사용 | DUO 미사용 |
|---|---|---|
| 시간 | 1,234초 | 289초 + 사람 답변 뒤 609초 |
| shell 명령 / web 검색 | 111 / 6 | 70 / 1 |
| DUO 호출 | 8(status 1, context 1, get_decision 2, review 4: index-required 1, PASS 3, 모두 task 없이) | 0 |
| 핵심 Decision 발견 | 찾음. context packet이 아니라 source 주석의 ID로 직접 조회 | 찾음. Decision 파일을 직접 읽음 |
| 사람 개입 | 0 | 1(좋은 질문 세 개로 멈춤) |
| 결과 | 승인된 acceptance criterion을 지킴 | 그 regression test를 완화하고 사람에게 알림 |
| `duoctl review --task` | PASS, ALIGNED 3 | 같은 PASS, ALIGNED 3 |

DUO는 결과를 결정하지 않았다. context packet에는 중요한 두 Decision과 핵심 파일이 빠졌고, review는 계약을 지킨 diff와 약화한 diff에 같은 PASS를 줬다. 방해도 없었다. DUO 때문에 불필요하게 멈춘 적은 없다. "review 결과에 따라 행동하라"는 지시 때문에, DUO를 쓴 세션이 사람에게 물어야 할 trade-off를 스스로 정했을 가능성이 있다.

## 14. Recommended next development

판정: **HOLD.** 정의상 P0(false PASS, authority 손실, Truth safety) 문제가 있다. Coordinator가 5개를 직접 재현했다.

HOLD의 범위:

- 새 기능, 0.4 작업, 다음 prerelease를 멈추고 P0 처리 범위부터 정한다.
- 0.3.0을 deprecate하거나 `latest`를 0.2.2로 되돌리는 권고는 아니다. C262와 C263의 원인은 0.2.2에도 있고, C261도 0.2.x의 lock 구조에서 왔을 가능성이 높다. 0.2.2로 되돌려도 이 위험이 사라지지 않는다.
- 위험의 전제: C261~C263은 누군가(사람이나 Agent)가 Truth 파일을 수정한 경우다. Truth 수정이 review 범위에 함께 들어오면 대부분 잡힌다. C264와 C265는 Truth 수정 없이도 생기며, CI처럼 깨끗한 checkout에서 전체 범위를 review하면 C264는 생기지 않는다.

이후 0.3.1 patch 후보(최대 3개, Human Decision으로 확정):

1. **Decision authority integrity**(C261, C262, C263): 모든 review·status·doctor·MCP에서 confirmed Decision 전체의 lock과 lifecycle 전이를 검증하고, `decisions/`에서 인식하지 못한 파일은 fail closed.
2. **평가하지 못한 내용으로 PASS 내지 않기**(C264, C265): import 검사는 reviewed side의 내용을 쓰고, gap 단계가 실패하면 PASS 대신 fail closed하고 모든 출력에 표시.
3. 선택: **`install remove`**(C266). 범위가 작고 위험이 낮다.

C259·C260·C267·C268·C269는 실제 workflow에서 반복된 signal 품질 문제다. 0.4 후보로 따로 다룬다.
