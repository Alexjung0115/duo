## 2. C261 — lifecycle authority bypass

**재현**(Coordinator, clean fixture, registry 0.3.0):

| 변형 | 결과 |
|---|---|
| lock이 유효한 confirmed block D-001을 `state: superseded`, `superseded_by: D-004`로 수정(D-004는 D-002를 supersede하고 자신도 superseded) + 같은 diff에 금지 import | **PASS**. `decision-integrity` ALIGNED "lock valid; only lifecycle fields changed" |
| 같은 수정, D-004가 다른 관계인 fixture | ASK(`decision-integrity` UNKNOWN 계열) — 결과가 fixture마다 다름 |
| `state: rejected`로 수정 + 같은 diff에 금지 import | **PASS, claim 0개** |
| `state: rejected`를 commit한 뒤 위반 | **PASS** |
| `state: proposed`로 수정(같은 diff 또는 commit) | WARN(pending surface뿐), 위반 claim 없음 |

**원인**(`packages/director/src/review/rules.ts`):

1. `decisionIntegrity`는 새 상태가 confirmed나 superseded가 아니면 그 Decision을 건너뛴다(`if (n.state !== "confirmed" && n.state !== "superseded") continue;`). confirmed → rejected/proposed 전이는 claim이 없다.
2. superseded로 바뀌었고 lock이 유효하면 ALIGNED `lifecycle-change-only`다. `superseded_by`가 가리키는 Decision이 실제로 이 Decision을 `supersedes`하는지 보지 않는다.
3. `supersedeIntegrity`는 새 Decision 쪽(`state: confirmed`이고 `supersedes`가 있음)에서만 검사한다.
4. authority 선택(`isActive`)은 state만 본다. lifecycle field는 digest 밖이므로(§1 B) lock이 유효한 채 authority가 사라진다.
5. loader와 status·doctor·MCP는 lifecycle 일관성을 보지 않는다.

**lifecycle을 digest에 넣을 수 있는가**: 의도된 계약(AC-009-03)이다. 넣으면 supersede 때 기존 Decision을 다시 잠가야 하고, 이미 저장된 superseded Decision의 lock은 confirmed 시점의 digest라 **모두 mismatch**가 된다. migration이 필요하다.

| Option | 내용 | 기존 Truth | 판단 |
|---|---|---|---|
| A | lifecycle field를 lock digest에 포함 | 저장된 superseded Decision 전부 깨짐, lock 형식 migration 필요 | 채택 안 함 |
| B | 기존 lock 유지 + 전이 증명(예: `superseded_by` 전용 digest나 서명) | 새 field, schema 변경, 기존 superseded Decision에는 증명이 없음 | 0.3.1에는 과함 |
| C | authority 작업 전에 lifecycle 상태와 supersession graph를 구조적으로 검증 | 정상 Truth는 그대로 통과(아래 확인) | **채택** |

Option C의 규칙(현재 상태, 파일만으로 판정):

- `lock`이 있는 Decision(한 번 confirm된 것)의 `state`는 `confirmed` 또는 `superseded`만 허용한다. `rejected`나 `proposed`로 돌아간 locked Decision은 오류다.
- `state: superseded`면 `superseded_by`가 있어야 하고, 그 ID의 Decision S가 존재하며, `S.supersedes`가 이 ID이고, S가 `confirmed` 또는 `superseded`(chain)여야 한다.
- `state: confirmed`인데 `superseded_by`가 있으면 오류다.
- 새 Decision이 `supersedes`를 갖지만 옛 Decision이 아직 confirmed인 반쪽 supersede는 authority 손실이 아니다(옛 Decision이 계속 집행됨). 기존처럼 범위 안에서 `supersede-integrity` PARTIAL로 둔다.

호환성 확인: OpenHub의 Decision 37개(모두 confirmed, lock 37개 valid), T65 C fixture 두 개(supersede chain D-002 → D-004 → D-005 포함)는 이 규칙을 모두 통과했다. 정상 supersede 절차(DecisionService)는 이 규칙을 만족하는 상태만 쓴다.

## 3. C262 — 범위 밖의 commit된 tamper

**재현**: lock이 있는 D-001의 `enforcement: block → warn`을 먼저 commit한 뒤 위반 → **WARN**, integrity claim 없음, status·doctor "ready". `forbids` 변경이나 파일 삭제를 먼저 commit → **PASS**(T65 C·D). 약화 commit이 review 범위에 들어가면 BLOCK + `decision-integrity`. 0.2.2도 같다(`forbids.dependencies`로 비교, 둘 다 WARN·integrity 없음).

**원인**: Decision integrity가 **diff-local rule**로만 구현됐다. `verifyDecisionLock`은 R-LOCK(diff 안의 파일)과 DecisionService에서만 불린다. `DECISION_LOCK_MISMATCH`는 severity가 warning이고 loader가 내지 않으므로 H-75 경계를 지나간다.

**작업별 감사**:

| 작업 | Truth 읽기 | lock 검사 | 권장 |
|---|---|---|---|
| review | `requireCompleteTruth` | diff 안만 | 현재 상태 전체 검증, 실패 시 verdict 없음 |
| context | `requireCompleteTruth` | 없음 | 같음(Context Packet은 Agent에게 authority를 전달한다) |
| adoption baseline | `requireCompleteTruth` | 없음 | 같음 |
| decision list | 허용 | 없음 | 오류를 표시(이미 읽지 못한 파일을 따로 적는 경로가 있음) |
| decision confirm/reject/review-pending | `requireCompleteTruth` | 대상만 | 같음. 다른 Decision이 invalid면 거부(기존 `PROJECT_TRUTH_INVALID`와 동일) |
| status | 허용 | 없음 | 0 유지, `Truth errors`에 표시 |
| doctor | 허용(`truthAuthorityErrors`) | 없음 | `truth.project: invalid`, 6 |
| MCP review·context | director 경유 | 위와 같음 | review·context와 같이 fail closed |
| MCP read tool(status, get_decision) | 허용 | 없음 | 오류 표시는 C270(이번 범위 밖, §11) |
| UI review | director 경유 | 위와 같음 | review와 같음(기존 `PROJECT_TRUTH_INVALID` 화면) |

**결론**: integrity는 repository current-state invariant여야 한다. 진단 명령은 파일을 읽고 invalid를 보여 주고, authority를 쓰는 작업은 부분 authority로 판정하지 않는다. 0.2.2의 `PROJECT_TRUTH_INVALID` 패턴과 그대로 통합된다. loader가 Decision 전체에 대해 lock 불일치를 error 진단으로 내면 위 표의 동작이 기존 코드 경로로 나온다.

**현재 상태만으로 탐지할 수 없는 것**(남는 한계, 문서화):

- confirmed Decision 파일 **삭제**: 흔적이 남지 않는다. 삭제가 review 범위에 있을 때(PR 단위 CI)만 `confirmed-decision-removed`로 잡힌다.
- **digest를 다시 계산한 위조**: lock은 서명이 아니다. 10-security의 "의도적으로 우회하는 적대적 Agent는 범위 밖"에 해당한다.
- **lock을 지운** confirmed Decision: ADR-013의 manual fallback과 구별할 수 없다. 범위 안에서는 기존처럼 UNKNOWN(drift). 현재 상태에서 막으면 fallback을 쓰는 저장소가 깨진다.

복구 경로(오류 메시지에 안내): 파일을 Git으로 되돌리거나, 사람이 의도한 변경이면 lock을 지워 manual confirmed 상태로 만든 뒤 `duoctl decision confirm <id>`로 다시 잠근다(ADR-013 기존 경로). 새 Decision으로 supersede하는 것이 원칙이다.

## 4. C261/C262 통합

하나의 invariant로 둔다: **"방향·준수 판단에 confirmed Decision authority를 쓰는 작업은, 그 전에 현재 authoritative Decision 집합 전체가 완전성·무결성 검사를 통과해야 한다."** 다음 중 하나라도 있으면 부분 authority로 판정하지 않는다.

- 읽지 못한 Decision(기존 H-75)
- lock 불일치(confirmed·superseded 전체)
- 잘못된 lifecycle(§2 규칙)
- 인식하지 못한 Decision 후보(§5)

구현 지점은 하나다. loader(또는 loader 직후의 Decision authority 검증)가 error 진단을 내고, 기존 `requireCompleteTruth`가 막는다. review rule에 범위 밖 검사를 따로 넣지 않는다. 범위 안의 R-LOCK claim(삭제·내용 변경·manual confirm)은 그대로 둔다.

## 5. C263 — authoritative 후보 경계

**loader의 현재 후보**(`packages/core/src/loader/project.ts`, `packages/core/src/domain/definitions.ts`):

| 파일(`.duo-project/decisions/` 아래, `proposals/` 제외) | 처리 |
|---|---|
| `*.yaml`, `*.yml`(대소문자 무시) | YAML Decision으로 엄격하게 parse. 잘못되면 `PROJECT_TRUTH_INVALID`(정상) |
| `*.md` | 정의 Markdown으로 parse. frontmatter의 `type`이 **정확히** `"decision"`일 때만 ADR형 Decision. 아니면 frontmatter 전체를 무시하고 일반 문서로 본다(본문의 metadata block은 계속 읽음) |
| 그 밖의 확장자(`.yaml.txt`, `.json` 등) | 읽지 않음 |

**재현**: `type: Decision`(대문자)이나 `type` 없음 + `id: D-001`, `state: confirmed`, `forbids`, `enforcement: block` → decisions 0, errors 없음, doctor ready, 위반 PASS. `type: decision`이면 BLOCK. 0.2.2도 무시하지만 missing-intent 때문에 WARN이었다. 원인은 H-80이 아니라 loader가 후보를 조용히 버리는 것이다. **H-80은 바꾸지 않는다.**

**정책**(Option A 채택):

- 지원 형식의 파일만 Truth 후보다: `decisions/`의 `.yaml`·`.yml`(기존 그대로)과 frontmatter가 Decision처럼 보이는 `.md`.
- `.md`가 Decision 후보인 조건: frontmatter의 `type`이 대소문자·공백만 다른 `decision`이거나, `type`이 `decision`이 아니면서(없음 포함) frontmatter `id`가 Decision ID(`D-###`)인 경우. 이 경우 오류(`PROJECT_TRUTH_INVALID` 경로, 새 진단 code)이고 authority 작업은 fail closed다.
- frontmatter가 없거나 Decision과 무관한 frontmatter를 가진 `.md`(README, 메모)는 지금처럼 일반 문서다.
- 지원하지 않는 확장자(`D-001.yaml.txt`)는 계속 Truth가 아니다. directory 안의 임의 파일을 authoritative로 넓히지 않는다(Option B 채택 안 함). T65에서 이것을 false negative로 셌지만, 계약상 Truth 파일이 아니다.

## 6. C264 — reviewed snapshot 불일치

**재현**:

| 경우 | 결과 |
|---|---|
| 금지 import를 stage, working tree 사본만 수정, `review --staged` | PASS + limitation `imports-reviewed-side-not-indexed`, `--fail-on block` 0 |
| 위를 commit, `--from HEAD~1 --to HEAD`(working tree 다름) | 같음 |
| working tree를 비운 같은 범위 | BLOCK |
| **(T66 신규)** 금지 import를 stage(working tree 같음), working tree에서만 D-001의 `forbids` 삭제(unstaged), `review --staged` | **PASS, limitation도 없음.** 같은 상태를 working tree로 review하면 BLOCK(`decision-integrity`) |

**입력별 출처**(`--staged` = HEAD → INDEX, `--to <ref>`):

| 입력 | 출처 |
|---|---|
| diff, 바뀐 줄 | reviewed side(Git) |
| `sideText`(dependency 규칙, R-LOCK의 옛 쪽) | 해당 side의 blob |
| Project Truth(`loadProjectTruth(root)`) | **working tree** |
| Graph·index(Symbol 범위, import 해석, diff seed) | **working tree** |
| import 분석(`decisionForbidsImport`) | working tree index. reviewed side 내용이 다르면 그 파일은 검사하지 않고 limitation |
| diff seed(`seeds.ts`) | reviewed side의 hunk 줄 번호를 working tree Symbol 범위에 맞춤. 불일치 검사 없음 |
| evidence 위치 | working tree 파일 |
| adoption baseline 비교 | baseline 기록(HEAD 기준) |

**원인**: reviewed side와 analysis snapshot(working tree)이 다를 수 있는데, import 규칙만 이를 알아채 limitation을 남기고, Truth와 diff seed는 알아채지도 못한다. import 규칙의 동작은 의도된 설계였다(주석 "The index describes the working tree").

**범위**: import 하나의 문제가 아니다. Truth(재현됨, limitation도 없는 false PASS)와 Graph 기반 규칙 전반(diff seed → Symbol forbids, requirement, scope)이 같은 구조다. 0.3.1에서는 재현된 두 경로(changed file, Truth)를 blocker로 둔다.

| Option | 내용 | 정확성 | 비용 |
|---|---|---|---|
| A | reviewed blob을 analyzer에 직접 넣어 분석 | 높음. 단 module 해석은 저장소 파일 집합과 설정이 필요해 reviewed side 전체가 필요함 | 큼(새 분석 경로) |
| B | 임시 snapshot worktree에서 분석 | 높음 | 큼(전체 index 비용, Windows 경로·성능) |
| C | snapshot이 다르면 그 review는 판정하지 않음(fail closed) | 높음(판정한 것은 맞음) | 작음 |

**권장(0.3.1)**: Option C를 모든 입력에 공통으로 적용한다. **reviewed snapshot contract**: `to`가 WORKTREE가 아닐 때, (1) diff의 바뀐 경로와 (2) loader가 읽는 Project Truth 파일(`decisions/proposals/` 포함, `reviews/`·`generated/`·`cache/`·`runtime/` 제외)이 reviewed side와 working tree에서 내용이 다르면 verdict 없이 실패한다. 오류는 다른 경로를 보이고 해결 방법(unstaged 변경 정리, 검토할 commit을 checkout)을 안내한다. DUO는 working tree를 stage하거나 고치지 않는다. diff 밖 파일만 다를 때는 판정하되, 기존 limitation 방식으로 "diff 밖 파일 N개는 working tree 기준"을 남긴다. Option A·B는 0.4 후보다.

영향: 다른 checkout에서 과거 commit을 `--from/--to`로 review하면 이제 실패한다. T65 B가 지적했듯 이 review는 이미 현재 index와 milestone을 써서 의미가 틀렸다. PR 단위 CI(검토할 commit을 checkout)는 영향이 없다. 부분 staging한 pre-commit은 안내에 따라 unstaged 변경을 정리해야 한다.

| diff | 필수 | 실패 | 그대로 |
| reviewed snapshot 일치 | 필수(신규, §6) | 검사 없음 | verdict 없음 |
| review context 컴파일(seed나 task가 있을 때) | 필수: Knowledge Gap 평가(ASK의 유일한 근거)와 규칙의 `reviewPacket` 입력 | 진단만, verdict 계산 | verdict 없음 |
| Knowledge Gap 평가 | 필수 | 위에 딸림 | verdict 없음 |
| task context 컴파일(task가 있을 때) | 필수: R-SCOPE 입력 | 진단만 | verdict 없음 |
| 결정적 규칙 | 필수 | 예외는 실패 | 그대로 |
| semantic assist | 선택(BLOCK을 만들지 않음, 결과를 따로 붙임) | 따로 표시 | 그대로 |
| Review Record 쓰기, metrics 쓰기 | 선택(별도 작업) | 따로 표시 | 그대로 |
| 언어별 분석 능력(L0/L1), adoption baseline 없음 | 문서화된 limitation | limitation | 그대로 |

**ASK로 바꾸지 않는다.** ASK는 사람의 선택이 필요하다는 판정이고, 분석 실패는 엔진의 실패다. 실패를 ASK로 바꾸면 사람이 답할 수 없는 질문이 생긴다.

**표면**: 새 result status를 만들지 않고 H-75와 같은 실패 경로(결과 없음 + 진단)를 쓴다. 그러면 표면이 저절로 일치한다. CLI는 verdict 없이 종료 코드 1과 진단(사람 출력·JSON), MCP는 `isError`와 진단 text, UI는 기존 `PROJECT_TRUTH_INVALID`류 실패 화면을 보인다. `--record`는 결과가 없으므로 Review Record를 쓰지 않는다(`REVIEW_NOT_RECORDABLE` 경로). 오류는 필요한 budget(packet frame token)과 `--budget`·`--files` 안내를 담는다. 큰 diff의 budget을 자동으로 늘리는 것은 동작 변경이라 이번 범위가 아니다.

## 8. C264/C265 통합

하나의 invariant로 둔다: **"review는 verdict에 쓰인 모든 입력이 reviewed snapshot을 기술하고 모든 필수 분석이 끝났을 때만 verdict를 낸다. 아니면 verdict 없이 실패한다."** 새 진단 code 두 개(예: `REVIEW_SNAPSHOT_MISMATCH`, `REVIEW_ANALYSIS_INCOMPLETE`)가 같은 실패 경로를 쓴다.

## 9. Threat model

10-security의 현재 가정: Coding Agent는 악의적이지 않지만 실수할 수 있다. DUO는 파일 쓰기를 막을 수 없고 보호는 탐지다. 의도적으로 탐지를 우회하는 적대적 Agent는 범위 밖이다.

T65가 보인 경로(lifecycle 수정, 약화 뒤 commit, Decision 형식 실수, staged/unstaged 차이)는 대부분 **실수로도 생기는** 변경이다. 실제로 gpt-5.5 세션 하나는 프로젝트 소유 spec을 스스로 고쳤다. 이것은 현재 위협 모델 안이며, 탐지가 범위 밖에서 일어나지 않는 것은 계약 위반이다.

결론:

1. OS 수준 쓰기 방지: DUO가 보장할 수 없다(변경 없음).
2. 탐지: DUO는 authority를 신뢰하기 전에 Truth의 현재 상태에서 탐지할 수 있는 무단 변경(lock 불일치, 잘못된 lifecycle, 인식하지 못한 후보)을 조용히 신뢰하지 않아야 한다.
3. 남는 한계: 삭제(범위 안에서만), digest 재계산 위조(적대적, 범위 밖), lock 삭제(manual fallback과 구별 불가). 10-security와 0.3.1 release notes에 적는다.

## 10. H-82 제안(기록하지 않음)

> **H-82 — 0.3.1 correctness patch after T65 adversarial dogfood.**
> (1) 새 기능 없음. (2) Patch Group A(authority integrity): C261, C262, C263. (3) confirmed Decision authority에 기대는 작업(review, context, adoption baseline, Decision lifecycle, 그리고 이들의 MCP·UI 경로)은 그 전에 현재 authoritative Decision 집합 전체가 완전성·무결성 검사를 통과해야 한다: 읽지 못한 Decision, lock 불일치, 잘못된 lifecycle·supersession, 인식하지 못한 Decision 후보 중 하나라도 있으면 `PROJECT_TRUTH_INVALID`로 verdict·Packet 없이 실패한다. status·doctor·decision list는 읽고 보여 준다. (4) DUO는 Agent의 저장소 쓰기를 막을 수 없지만, 현재 상태에서 탐지할 수 있는 무단 변경을 조용히 신뢰하지 않는다. 삭제(범위 안에서만), digest 재계산 위조, lock 삭제는 남는 한계로 문서화한다. (5) 지원 형식의 Truth 후보(`decisions/`의 `.yaml`·`.yml`, Decision처럼 보이는 frontmatter의 `.md`)가 Decision으로 읽히지 않으면 진단과 fail closed다. 지원하지 않는 파일은 Truth가 아니다. (9) 필수 분석(review·task context 컴파일, Knowledge Gap 평가)이 실패하면 PASS도 ASK도 내지 않고 verdict 없이 실패한다. CLI·JSON·MCP·UI가 같은 실패를 보이고 Review Record를 쓰지 않는다. (10) H-80은 바꾸지 않는다. (12) 0.3.0은 검증된 0.3.1이 준비될 때까지 `latest`로 둔다. 0.2.2로 되돌리지 않는다. (13) 0.2.3 backport는 하지 않는다. 지원 정책상 필요가 생기면 따로 결정한다. (14) External Validation 01은 정확히 0.2.1이다. (15) C266 이하와 0.4 작업은 제외한다.

## 13. 0.3.1 acceptance criteria(제안)

Authority(Group A):

- A1 정상 confirmed Decision(lock 유효): 기존 동작 그대로(BLOCK·WARN·PASS·context 동일).
- A2 현재 상태의 lock 불일치(범위 밖 commit 포함): review·context·baseline·confirm은 `PROJECT_TRUTH_INVALID`로 verdict 없이 실패. status는 0과 오류 표시, doctor 6.
- A3 tamper를 review 범위 이전에 commit: 여전히 탐지(A2).
- A4 잘못된 lifecycle(lock이 있는 Decision을 superseded·rejected·proposed로 손으로 바꿈, 잘못된 `superseded_by`): authority 우회 없음(A2와 같은 실패). 범위 안이면 R-LOCK claim도 남음.
- A5 `duoctl decision`(CLI·UI·review-pending)으로 한 정상 supersede와 chain(D-002 → D-004 → D-005): 동작 그대로.
- A6 Decision처럼 보이지만 인식하지 못한 `.md`(`type: Decision`, `type` 없음 + `id: D-###`): 진단을 보이고 fail closed.
- A7 지원하지 않는 파일(`D-001.yaml.txt`), frontmatter 없는 `decisions/README.md`: 프로젝트를 invalid로 만들지 않음.
- A8 lock 없는 manual confirmed Decision(ADR-013 fallback): 기존 동작 그대로(범위 안 UNKNOWN drift).
- A9 confirmed Decision 삭제가 범위 안에 있음: 기존처럼 `confirmed-decision-removed` BLOCK.

Review completeness(Group B):

- B1 `--staged` 금지 import, working tree 다름: verdict 없이 실패(다른 경로 표시). PASS 없음.
- B2 working tree가 같은 `--staged`: 기존처럼 BLOCK.
- B3 working tree가 같은 `--from/--to` commit 범위(CI): 기존 결과 그대로.
- B4 `--staged` + working tree에서만 Truth 변경: verdict 없이 실패.
- B5 필수 context·gap 분석 실패(5,000 파일 + declared UNKNOWN): PASS·ASK 없이 실패, 필요한 budget 안내, `--fail-on`과 관계없이 verdict 종료 코드가 아님.
- B6 같은 실패가 CLI 사람 출력, CLI JSON, MCP(`isError`와 text), UI에 모두 보임.
- B7 실패한 review에 `--record`: Review Record를 쓰지 않음.
- B8 diff 밖 파일만 working tree와 다른 `--staged`: 판정하고 limitation 표시.

Compatibility:

- C1 정상 Truth는 byte 그대로(검사는 읽기만 함).
- C2 re-init·migration 없음.
- C3 upgrade 0.2.2 → 0.3.1(`release:upgrade`).
- C4 npm 10/11/12 global, npm 11 local 설치 matrix.
- C5 CI 3 OS.
- C6 실제 Truth(OpenHub, Decision 37개)와 T65 fixture의 정상 경우가 그대로 통과.
- C7 External Validation 01은 0.2.1 그대로.
