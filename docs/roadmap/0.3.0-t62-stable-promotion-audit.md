## 5. 그 밖의 T61 finding

- **scope-relevance `outside-task-context` UNKNOWN**: task에 실제로 포함된 파일(barrel export, MCP renderer)이 task 밖으로 판정됐다. BLOCK 아님, H-80과 무관, blocker evidence 없음. F-26과 원인이 다르므로 별도 C-ID 후보(C260 제안, 이번에 기록하지 않음).
- **install launcher**: OpenHub가 commit한 `npx --no-install duoctl`(project-local 0.2.1)을 global rc.6 install이 `duoctl`로 바꿨다. 코드상 Claude Code는 `compatible-different-format`(managed, "an older or different DUO launch; it is replaced"), Codex는 DUO 관리 블록 안의 `drifted`로 분류하고, DUO가 아닌 command는 conflict로 덮어쓰지 않는다(H-36 조항과 일치). `--yes` 없이는 아무것도 쓰지 않고 "MCP entry (.mcp.json): compatible-different-format → modify"와 launcher를 보여 주며, JSON plan에는 current·planned 값이 있다. 분류: correctness 아님, destructive 아님(보이는 plan, `--yes` 필요, Git으로 되돌림), team reproducibility 우려(고정 version 우회). post-0.3 UX(사람용 plan에 바뀌는 launcher 값과 project-local → global 경고 표시). blocker 아님.
- **review-pending 길이**: 8개 preview 318줄·약 18.8k자, 정확성 문제 없음. post-0.3 UX 후보.
- **agent 해석**: Codex가 4개 verdict와 gap의 역할을 모두 정확히 설명했다. BLOCK 답변의 "no confirmed requirement or decision explaining the intent"는 MCP text("The context DUO assembled contains …")를 LLM이 풀어 쓴 표현이다. renderer 출력은 정확하므로 LLM paraphrase 한계로 분류하고 blocker로 올리지 않는다.

## 6. External Validation

## 7. Stable의 의미와 source

- 의미: 0.3 line의 권장 일반 공개 버전, npm `latest` → 0.3.0, rc.6에서 검증한 semantics의 승격, 새 기능 없음. 시장 thesis 증명, WARN noise 0, External Validation 성공, 모든 저장소에 `--strict` 권장, 완전한 언어 지원을 뜻하지 않는다.
- **source 제약(감사 결과)**: release tooling(`scripts/release/channel.mjs`, H-70·T43.1)은 version만으로 channel을 정하고 override가 없다. stable(`0.3.0`)은 branch `main`, upstream `origin/main`, dist-tag `latest`에서만 잘린다. 그러므로 task가 추천한 "next HEAD에서 0.3.0 version commit"(Option A)은 preflight `git-branch` blocker이고, rc.6 tag에서 따로 만든 release branch(Option B)도 같은 이유로 막힌다.
- **추천 source(Option C)**: H-81 승인으로 `next`를 `main`에 merge한다. 제품 tree(`packages/`, `apps/`, `scripts/`, `package.json`, `pnpm-lock.yaml`)는 rc.6(`d0f29a5`)과 같게 두고, 그 위에 version 0.3.0 commit을 만든다. T61 보고서 같은 docs-only 이력은 함께 들어온다.
- merge 감사: merge-base `c163e80`, `next`에만 62 commit, `main`에만 20 commit. main 전용 제품 변경은 0.2.2 security patch(fail-closed Truth, MCP SDK 2.2.0)이고 같은 수정이 `next`에 있다(`authority.ts`·`authority.test.ts`는 두 branch에서 동일, `requireCompleteTruth`, SDK 2.2.0). main에만 있는 것은 test `tests/cli/truth-fail-closed.e2e.test.ts`와 release 문서(H-74 행, checklist, notes-0.2.2 등)다. 제품 파일 충돌은 rc.6 쪽으로 해결하고, 문서는 양쪽 행을 모두 보존하며, main 전용 test는 rc.6 코드에서 통과하면 유지한다(test는 package에 들어가지 않는다).
- **product delta 허용**: 0.3.0-rc.6 → 0.3.0은 version(`apps/cli/package.json`, `npm-shrinkwrap.json`)과 release 문서뿐. merge 결과의 제품 tree와 `d0f29a5`의 diff가 version 외에 하나라도 있으면 중단하고 새 RC가 필요하다.

## 8. Stable notes와 알려진 한계

stable notes는 rc.3~rc.6 changelog를 붙이지 않고 0.2.2 대비로 압축한다: Human 확정 full Decision workflow(제안의 forbids·enforcement·supersedes, informed confirm), forbidden imported paths(H-72), `decision review-pending`, Issue `implements.paths`(H-78), 명시 seed 보존(H-76), exact path·symbol precision(C249·C251·C252·C256), root file path(H-79), Decision authority 표시(C241), missing-intent 신호 정정(H-80·C258), fail-closed safety floor 0.2.2, 호환·업그레이드.

알려진 한계(현재 상태 기준):

- outside-current-milestone PARTIAL WARN(C259): milestone 관리 저장소에서 `--strict` 도입 전 확인
- 구분자·점이 없는 root file(`LICENSE`, `Dockerfile`)은 `./` 필요
- secret file(`.env*` 등)은 index되지 않음
- `imported_paths`: barrel·re-export 경유 false negative, Java·C# imports 미검사
- provenance 값 `introduced`를 agent가 "이번 변경이 만듦"으로 읽을 위험(사람 표시는 H-73 용어)
- Node.js `>=24.15.0`
- package 크기 약 24 MB packed / 114 MB unpacked(67 runtime dependency bundle)
- C++ IMPORTS include path(C232), Java·C#·C++·Python은 L1

## 9. Release-process guard

T60 사고(문서 삽입 helper가 자기 source를 넣음)는 제품에 영향이 없었지만 release authorization 문서에서 실제로 일어났다. stable publish 전에 tooling-only guard를 T63에 포함할 것을 권한다: preflight 또는 publish 전 단계에서 `docs/conflicts.md`에 대상 commit SHA와 version을 담은 Human Decision 행이 있는지, `docs/release/checklist.md`에 같은 SHA·version이 있는지, 두 파일에 helper 코드 패턴(`require(`, `process.argv`, `readFileSync` 등)이 없는지 assert한다. release script만 바꾸며 package artifact는 바뀌지 않는다(`scripts/`는 package `files`에 없음). 같은 task에서 compatibility에 0.2.2 → 0.3.0 누적 분류 절을 추가한다.

## 10. 판정

**PROMOTE-WITH-GUARD.** 제품 stable blocker는 0이다. stable publish 전 선행 조건은 모두 tooling·process·문서다.

1. H-81 승인(`next` → `main` merge 권한 포함, H-70(C))
2. 제품 tree = rc.6 merge와 그 diff assert
3. release authorization guard
4. compatibility 누적 절·stable notes

## 11. H-81 제안 문구 (기록하지 않음)

> H-81 — 검증된 0.3.0-rc.6 line을 stable 0.3.0으로 승격한다.
>
> 1. rc.6(`d0f29a5`)의 product semantics를 stable로 승인한다.
> 2. stable package에 rc.6 이후 새 product feature·fix를 넣지 않는다.
> 3. 근거: T61 dogfood 실제 review 23개, 잘못된 verdict 0, correctness blocker 0, H-80 noise 감소 확인. T60 packed·registry gate.
> 4. F-26/C259(outside-current-milestone WARN noise)는 known limitation으로 받아들이고 0.3 이후 재평가한다.
> 5. `--strict`를 모든 저장소에 무조건 권장하지 않는다.
> 6. stable은 H-70 channel 정책대로 `main`에서 자른다. 이를 위해 `next`를 `main`에 merge한다. 제품 tree(`packages/`, `apps/`, `scripts/`, `package.json`, `pnpm-lock.yaml`)는 `d0f29a5`와 version을 빼고 같아야 하며, 다르면 승격을 멈추고 새 RC를 만든다. 문서는 양쪽 이력을 모두 보존한다.
> 7. npm `0.3.0` → dist-tag `latest`. `next` dist-tag와 0.3.0-rc 공개물은 보존한다.
> 8. annotated tag `v0.3.0`과 stable GitHub Release(prerelease false, latest).
> 9. `v0.2.2` tag·Release는 보존한다. downgrade floor는 0.2.2다.
> 10. External Validation 01은 정확히 0.2.1로 계속하며 참가자를 자동으로 옮기지 않고 0.3.0을 안내하지 않는다.
> 11. stable 후보 commit에서 full stable release gate를 다시 실행한다(verify, conformance·C209, audit, repack, upgrade 0.2.0·0.2.2, npm 10/11/12 matrix, downgrade, 3 OS CI, preflight READY with releaseChannel stable).
> 12. publish 전에 release authorization guard(H-81 행·checklist의 SHA·version 존재, helper 코드 패턴 없음)를 둔다.
