## 6. CLI-FRICTION

사람 판단이 필요 없는데 사람이 하거나 Agent가 셸로 우회해야 하는 단계:

1. **index 갱신**: 코드가 바뀔 때마다 필요. MCP로는 불가능해 Agent가 셸에서 `duoctl index`를 실행한다(13번). 확정 뒤에도 DUO가 사람에게 "Run duoctl index"를 권한다(2번).
2. **설정이 네 단계**: `npm install -g` → `duoctl init`(질문 4개) → `duoctl install codex`(확인 1) → `duoctl doctor`, 그리고 결과 commit과 Codex trust.
3. **연결 해제가 끝나지 않음**: `install remove codex`가 성공이라고 하지만 `.codex/config.toml`의 MCP 항목을 남긴다(아래 Issue E).
4. **Decision 확정 주변 정리**: 확정은 사람이 하지만, 터미널 이동과 확정 뒤 index는 정리 작업이다.

## 14. Proposed zero-friction architecture

DUO의 서명(Human decides, Agent implements, DUO checks)은 그대로 두고, 사람이 하던 정리 작업만 없앤다.

1. **Agent-native 기본 경로**: Agent → MCP(또는 CLI fallback) → DUO. bridge 안내는 MCP tool 이름과 CLI 대안을 함께 적는다(이미 Agent가 자연스럽게 CLI로 바꿨다).
2. **안전한 자동 index(Option B 우선)**: MCP의 context·review가 stale index를 만나면 incremental index를 한 번 실행하고 진행한다. index는 재생성 가능한 상태이고, 중간에 죽어도 기존 index가 유지되는 것은 T65에서 확인했다. CLI 기본은 지금처럼 명시적(`--refresh`)으로 두어 CI 결정성을 유지한다. 동시 실행(여러 Agent)은 index lock으로 직렬화해야 하며, 이것은 구현 전에 확인할 조건이다. Truth는 절대 쓰지 않는다. 평가: 결정성(같은 결과, index만 갱신), 예상치 못한 write(`.duo-project/` 재생성 영역뿐), 성능(incremental 2~12초), 동시성(lock 필요), 손상 복구(기존 원자적 교체), CI(영향 없음, CLI 명시 유지), working tree(읽기만).
3. **한 명령 설정**: `duoctl setup`이 Git 확인 → init(질문은 사람 선택이 필요한 것만, 나머지는 기본값) → index·baseline → 설치된 Agent 감지 → 연결 계획 표시와 한 번의 확인 → 적용·검증 → "다음은 Codex에서 trust" 한 줄 요약. 기존 `init`·`install`은 고급·script용으로 유지.
4. **승인 UX**: proposal 뒤 Agent가 승인용 한 줄(또는 `duoctl ui` 링크)을 보이고, 사람은 미리보기 확인과 ID 입력만 한다. 확정 뒤 DUO가 index를 갱신한다. 여러 pending은 `review-pending`으로 한 번에.
5. **복구**: stale index는 자동, analysis incomplete는 Agent가 범위를 줄여 재시도, Truth·snapshot 문제는 사람에게 정확한 선택지를 보인다.

### Issue A — [UX] Make DUO nearly invisible during normal coding-agent workflows

Labels: `enhancement`

**Problem**
After setup, DUO still depends on people and agents remembering housekeeping steps: refreshing the index after code changes, running review, and running `duoctl index` again after every Decision confirmation. Decisions need a human, but these steps do not.

**Current experience**
In a 0.3.1 audit with Codex on three public repositories, nobody typed a DUO command during normal coding tasks. The agent followed the AGENTS.md block instead and ran `duoctl index` 13 times in 7 tasks through the shell; 4 of those were recoveries after `context` failed on a stale index. The MCP server has no way to refresh the index, so an MCP-only client or a read-only sandbox stops at `INDEX_REQUIRED`. Every Decision confirmation ends with "Run duoctl index so review and context see it."

**Expected experience**
After setup, the user asks the agent for a change in plain words. DUO's status, context, index refresh and review happen without the user. The user is interrupted only to decide (confirm or reject a Decision) or when DUO cannot safely continue.

**Why it matters**
Every manual step is a reason to stop using DUO, and each one teaches the user a DUO concept they should not need.

**Acceptance criteria**
- Normal coding task: 0 DUO commands typed by the user; the agent obtains context and a review.
- Stale index in the normal safe case: recovered automatically, no manual `duoctl index`.
- A Decision that needs a human: at most 1 deliberate approval interaction, no follow-up housekeeping.
- Concepts a new user needs before the first useful result: at most 3.
- Sub-issues below are closed or explicitly deferred.

**Non-goals**
Automatic Decision confirmation, silently editing Project Truth, hiding BLOCK or turning ASK into PASS, making DUO an autonomous coding agent.

**Relevant evidence**
T69 audit (`docs/roadmap/0.3.1-t69-zero-friction-ux-audit.md`): action counts and agent transcripts.

**Sub-issues**
One-command setup; automatic stale-index recovery; noisy WARNs; README-edit WARN; agents not finding DUO tools; `install remove`.

First-time setup takes four commands and two follow-ups.

**Current experience**
`npm install -g @duo-director/cli` → `duoctl init` (4 questions) → `duoctl install codex` (1 confirmation) → `duoctl doctor`, then commit the generated files and trust the project in Codex. Each step prints the next one. In the audit this took about 3 minutes per repository, and the Codex trust step is easy to miss because it happens outside DUO.

**Expected experience**
One command (for example `duoctl setup`) checks the repository, adopts it, builds the index and baseline, detects installed agents, shows one integration plan, applies it after one confirmation, verifies it, and ends with a single summary that names what is left (such as trusting the project in Codex). Questions are asked only for choices a person must make; safe defaults are used otherwise.

**Acceptance criteria**
- At most 1 DUO command after `npm install` for a repository with Codex or Claude Code installed.
- Human-owned choices (accepting a README suggestion as the project goal, policies) are still asked, never assumed.
- Nothing is written before the person confirms the plan; the existing `init` and `install` commands keep working for scripts.
- The final summary states the remaining manual step outside DUO, if any.

**Non-goals**
Changing Codex trust or Claude Code approval on the user's behalf. Committing files.

**Relevant evidence**
T69 audit §2 and §7.

### Issue C — Recover a stale index automatically when it is safe

Labels: `enhancement`

**Problem**
Context and review refuse to run on a stale index, and only the CLI can refresh it.

**Current experience**
After any code change, `duo_get_context` and `duo_review_changes` return `INDEX_REQUIRED`. The MCP interface has no index tool or refresh option, so agents leave MCP and run `duoctl index` in a shell (13 times in 7 tasks in the audit). Without shell access the workflow stops. After confirming a Decision, DUO asks the person to run `duoctl index`.

**Expected experience**
When the index is stale and it is safe to update it, DUO runs an incremental index once and continues. The result says that the index was refreshed. CI keeps an explicit, deterministic mode.

**Acceptance criteria**
- MCP context and review on a stale index: refreshed once and answered, with a visible note; no manual command.
- Never touches Project Truth or the working tree; only DUO's regenerable index state.
- Two agents at once do not corrupt the index (serialized or one waits).
- CLI keeps today's explicit behavior by default (`--refresh`), so CI results do not change.
- An index that cannot be refreshed safely still fails with a clear reason.

**Non-goals**
Background file watching, automatic Truth repair.

**Relevant evidence**
T69 audit §5 and §6.

### Issue D — Reduce noisy WARNs in normal milestone and task workflows

Labels: `enhancement`

**Problem**
Normal, correct changes get WARN for reasons that do not help the person reviewing them.

**Current experience**
- In a repository that tracks Requirements by milestone, editing a file that implements a Requirement of another milestone gives a WARN. In one real repository this was 12 of 20 normal commits.
- With a natural-language task, the file the task is about can be reported as outside the task (seen in 0.3.1: the task named `HTTPError` and `source/errors/HTTPError.ts` was "outside-task-context"; in an earlier audit, 8 of 22 natural-task reviews).
- `--strict` (`--fail-on warn`) in CI fails these correct changes.

**Expected experience**
A WARN means something a person should look at. Normal work on the current task and on implemented Requirements does not need attention.

**Acceptance criteria**
- A reproducible fixture for each pattern, added to the test suite.
- On those fixtures the normal change is not WARN, and real out-of-scope or conflicting changes still are.
- No change to BLOCK, ASK or PASS semantics for Decisions.

**Non-goals**
Hiding claims; the facts stay available in verbose output.

**Relevant evidence**
Internal C259, C260 (`docs/conflicts.md`); T61, T65, T69 audits.

### Issue E — `duoctl install remove` leaves the DUO MCP server configured

Labels: `bug`, `good first issue` (candidate)

**Problem**
Removing the Codex (or Claude Code) integration reports success but leaves the MCP server entry when DUO created the config file.

**Steps to reproduce**
1. In a repository without `.codex/config.toml`, run `duoctl init` and `duoctl install codex`, answer `y`.
2. Run `duoctl install remove codex`, answer `y`.
3. `.codex/config.toml` still contains the `[mcp_servers.duo-director]` block; `duoctl install status codex` says `drifted · MCP already-configured`.

**Current experience**
The plan says `delete .codex/config.toml`; the result line says `modify .codex/config.toml`; the file is unchanged. Only the AGENTS.md block is removed. Seen 4 of 4 times in one audit and again in 0.3.1.

**Expected experience**
The file DUO created is deleted (or the DUO block is removed if the file has other content), the result matches the plan, and `install status` reports not connected.

**Acceptance criteria**
- Test: install then remove leaves no DUO block and no file DUO created, for Codex and Claude Code.
- Files that existed before install keep their other content byte for byte.
- The command's result line matches what was done.

**Relevant evidence**
Internal C266; T65 audit; T69 audit §13.

### Issue F — Editing README after setup makes every review WARN

Labels: `bug`

**Problem**
If you accept `duoctl init`'s suggestion to take the project goal from the README, any later README edit makes reviews WARN with `external-source-drift`, and there is no clear way to clear it.

**Steps to reproduce**
1. `duoctl init` in a repository with a README; answer `y` to "Use the suggestion?".
2. Change any part of the README and run `duoctl review`.
3. Result: WARN, `PARTIAL external-source-drift .duo-project/intent/vision.md · external-source-changed`.

**Current experience**
In the 0.3.1 audit, all 3 WARN results across two repositories came only from this, after agents updated README documentation as part of normal feature work. The agents told the user the vision "may need re-confirming", but DUO does not say how.

**Expected experience**
Unrelated README edits do not WARN, or the WARN says exactly what changed relative to the confirmed goal and how to accept it.

**Acceptance criteria**
- A README edit that does not touch the adopted sentence does not WARN.
- When the adopted text changes, the claim names it and the output shows how a person accepts the new text.
- Existing drift detection for real changes stays.

**Relevant evidence**
T69 audit §11.

### Issue G — Coding agents often don't find DUO's MCP tools and fall back to the CLI

Labels: `enhancement`, `documentation`

**Problem**
With DUO connected through `duoctl install codex`, the agent often says DUO's tools are not in its tool list and uses `duoctl` in the shell instead. Without the tools it cannot propose Decisions (the CLI has no propose command).

**Current experience**
In the audit, 3 of 7 Codex tasks used the DUO MCP tools; 4 fell back to the CLI. A diagnostic session found the tools only inside Codex's code runner (`tools.mcp__duo_director__…`), not under the names the AGENTS.md block uses. This depends on the Codex configuration.

**Expected experience**
The agent reliably finds DUO's tools, or the bridge text tells it exactly how to reach them and what to do when they are missing.

**Acceptance criteria**
- The AGENTS.md / CLAUDE.md block covers both tool names and the CLI fallback, including how to ask the human to confirm a proposal when the propose tool is missing.
- A documented check (`duoctl doctor` or a short guide) that shows whether the agent can see the tools.
- Measured again on Codex and Claude Code; results recorded.

**Non-goals**
Changing Codex or Claude Code themselves.

**Relevant evidence**
T69 audit §12; T65 (5 of 15 sessions).
